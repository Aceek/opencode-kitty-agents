# V1 Architecture

## Goals

- Present every relevant OpenCode child session in a Kitty split.
- Attach to the existing child session rather than creating another agent.
- Preserve focus on the orchestrator by default.
- Clean up managed windows safely when sessions disappear or the plugin stops.
- Keep session lifecycle logic independent from Kitty.
- Leave a narrow adapter seam for future presentation backends.

## Non-Goals

- OpenCode sidebar or TUI panel integration.
- Hyprland, tmux, WezTerm, or generic terminal support.
- Team communication, task orchestration, or agent prompt injection.
- Starting, stopping, or deleting OpenCode child sessions.
- Persisting recoverable control capabilities across process restarts.
- Automatically changing a user's Kitty layout.

## Core Contracts

```ts
type ChildSession = {
  id: string
  parentID: string
  directory: string
  title: string
  status: "idle" | "busy" | "retry"
}

type PresentationHandle = {
  backend: "kitty"
  windowID: number
  openedAt: number
}

interface PresentationAdapter {
  availability(): Promise<
    | { available: true }
    | { available: false; reason: string }
  >
  open(session: ChildSession, serverUrl: URL): Promise<PresentationHandle>
  exists(handle: PresentationHandle): Promise<boolean>
  focus(handle: PresentationHandle): Promise<void>
  close(handle: PresentationHandle): Promise<void>
  dispose(): Promise<void>
}
```

The exact TypeScript shapes may evolve during implementation, but the ownership
boundary must remain: the session controller never invokes Kitty directly.

The Phase 4 controller captures the live OpenCode server URL immediately before
each launch and passes that exact validated value to `open`; adapters do not
cache `ctx.serverUrl`.

## State Model

The controller owns one record per child session:

```ts
type ManagedChild = {
  session: ChildSession
  presentation?: PresentationHandle
  desired: "open" | "closed"
  phase: "discovered" | "opening" | "open" | "closing" | "unavailable"
  lastError?: string
}
```

State mutations run through one serialized queue. SDK calls and Kitty commands
may execute asynchronously, but their resulting mutations re-enter the queue
and verify that the record is still current.

## Session Discovery

Per ADR 0005, V1 tracks only immediate children of one active orchestrator
root, not every historical child visible to the project-scoped OpenCode client.
The tracker begins without an active root and never chooses one from list
recency.

- A live root `session.created` selects its own ID as the active root.
- A live child `session.created` selects its `parentID` as the active root.
- A creation below a known or pending immediate child is a nested descendant,
  not a root-selection signal; it cannot replace the active root.
- An unknown live `session.status` is resolved through a successful
  authoritative list and selects scope only when that exact session is a root
  with no `parentID`. Unknown child status never selects its parent.
- On `session.deleted`, remove only an immediate child of the active root. An
  active-root deletion clears scope and every published child.
- At startup and periodically, call `session.list()`, but publish nothing until
  a live event has selected scope. Once selected, retain only sessions whose
  `parentID` exactly equals the active root.
- Within that exact parent scope, admit a child only after observing its live
  `session.created` during this runtime or finding a valid `busy`/`retry` entry
  for it in a successful authoritative `session.status()` snapshot.
- Retain admitted eligibility when later status is idle or missing, normalizing
  a missing status for an admitted listed child to `idle`, until child deletion
  or committed root switch.
- Keep explicit child eligibility pending by candidate root until commit so a
  child created and completed before its first list/status snapshot remains
  eligible. Never transfer pending or committed eligibility across roots.

Reconciliation is authoritative for membership within the event-selected
scope. Root selection remains pending until successful list and status
snapshots atomically commit the root, eligibility, complete filtered membership,
and normalized status. A list or status failure during a switch leaves the
current root and children published; a successful status snapshot can still
update current eligible status when list fails. Neither failure consumes
pending root or eligibility intent. A successful switch replaces old-root
membership and clears old/foreign eligibility so the controller closes its
presentations. Active-root deletion still clears immediately from its
authoritative complete event payload.
Foreign created, deleted, status, and reconciled sessions cannot enter the
published immediate-child snapshot. Events establish scope and reduce latency;
historical snapshots alone never establish scope.

Every reconciliation captures a scope generation when requested. Receipt of a
deletion for the active or pending root, or for a child whose exact `parentID`
matches that root, synchronously increments the generation before the deletion
mutation enters the serialized queue. A foreign child's deletion does not
invalidate current scope. Generation checks after each SDK await and immediately
before commit ensure the now-stale result cannot publish while deletion waits
behind it. Only the scalar invalidation is synchronous; root, eligibility,
membership, and status maps remain queue-owned. A different explicit root
creation also invalidates stale in-flight scope work; duplicate creation for the
already expected root does not repeatedly invalidate.

A valid `session.status` for an ID not currently tracked as an active child
conservatively invalidates in-flight reconciliation before its resolution
mutation is queued. The event carries no parent data, so this invalidation does
not itself select scope; the later successful list must still prove the exact ID
is a root. Status for a known active child remains an ordinary serialized status
update and does not invalidate current reconciliation.

The plugin hook synchronously filters event types before calling the tracker.
Only `session.created`, `session.deleted`, and `session.status` may allocate
tracker queue work; unrelated event floods return immediately.

The Phase 3 tracker exposes only this controller-facing observation contract:

```ts
type SessionTrackerSnapshot = Readonly<{
  revision: number
  sessions: readonly ChildSession[]
}>

snapshot(): SessionTrackerSnapshot
subscribe(listener: (snapshot: SessionTrackerSnapshot) => void): () => void
```

Snapshots are sorted and immutable. A created event can be retained internally
without publishing it until a status event or successful status snapshot gives
it a normalized status. Unknown status events trigger full reconciliation.
Membership replacement requires both a successful `session.list()` response
and a valid successful `session.status()` map so membership, eligibility, and
status commit atomically. Missing status entries imply idle only for admitted
listed children; a failed or malformed status response causes neither that
inference nor membership replacement.

For presentation publication, successful list membership is further gated by
the active-root eligibility rule above. Consequently, selecting an old root does
not publish its historical idle children. Historical children currently busy or
retrying can be admitted from status authority, and admitted children remain
published through later idle/missing status transitions.

The installed OpenCode 1.18.4 SDK uses field-style responses: both calls return
an object whose successful `data` is respectively `Session[]` and
`Record<string, SessionStatus>`; failures may be returned in `error` or reject.
Its generated method option is an `Options<...>` object extending request
options, so cancellation is passed as the top-level shape `{ signal:
AbortSignal }`, not as query data. The tracker wrappers call exactly
`client.session.list({ signal })` and `client.session.status({ signal })`.
The tracker consumes those response envelopes without retaining request,
response, or error objects. Every SDK call receives a cancellation signal and
is independently raced against a 10-second tracker deadline because SDK 1.18.4
disables its generated transport timeout. Reconciliation requests share one
active-or-pending promise; duplicate ticks and events therefore cannot append
reconciliation work to the serialized queue. Event mutations request that work
only after leaving the queue, avoiding a recursive queue deadlock.

The tracker starts one reconciliation immediately and one periodic timer before
returning its hooks. Disposal clears the timer, stops accepting mutations,
immediately prevents commits, aborts active SDK requests, and bounds the drain;
noncompliant late completions are contained and cannot commit. Subscriber
dispatch does not await callbacks, while containing both synchronous throws and
asynchronous rejections. No presentation contract is referenced by the tracker.

## Kitty Targeting

The ADR 0004 background broker captures and validates the origin identity. It
alone owns `KITTY_LISTEN_ON`; the plugin receives only an owner-private,
randomly named Unix endpoint. The broker launches the OpenCode orchestrator,
then stores its returned numeric window ID as the presentation origin.

All commands target stored numeric IDs:

```text
origin tab:  --match=window_id:<origin-window-id>
source:      --source-window=id:<origin-window-id>
target tab:  --match=window_id:<origin-window-id>
placement:   --next-to=id:<selected-positive-window-id>
child:       --match=id:<child-window-id>
```

Never target `active`, `recent`, `-1`, titles, or indices.

## Child Command

The Kitty adapter launches a trusted executable with an argv array equivalent
to:

```text
opencode attach <server-url> --dir <directory> --session <session-id>
```

Resolve the OpenCode executable once when the trusted broker process is
constructed. The version 1 protocol has no executable or environment field, so
the executable cannot vary per session request. Do not use `/bin/sh -c`, copy a
complete environment, or place credential values in Kitty argv.

Kitty's launch implementation starts from its `default_env`, so removing only
selected variables is insufficient. Every OpenCode launch therefore executes
`/usr/bin/env -i` before the fixed executable. The broker supplies only a fixed
construction-time allowlist of terminal metadata, `HOME`, `PATH`, locale,
standard XDG directories, and path-only OpenCode configuration variables. The
orchestrator additionally receives the private broker endpoint and uses
`--cwd=current` with the exact invoking source window. Attached clients receive
no endpoint. Credentials and Kitty capabilities are never included; authenticated
server attach remains unsupported until a non-argv, non-IPC mechanism is
verified.

## Broker Protocol

The production broker uses newline-delimited JSON over one request per private
Unix connection. Every message has `version: 1`, exact keys, and a maximum size.
The only operations are `availability`, `open`, `exists`, `focus`, `close`, and
`shutdown`.

`open` accepts only the server URL (without URL credentials), directory,
session ID, split direction, numeric bias, and focus policy. Numeric child IDs
returned by `open` are the only IDs accepted by subsequent lifecycle requests.
No request can contain a Kitty command, match expression, executable, argv, or
environment map. Responses contain only operation results, numeric window IDs,
booleans, and bounded error codes.

The endpoint must be an owner-only socket named
`opencode-kitty-agents-<random>/broker.sock` under an owner-controlled
`XDG_RUNTIME_DIR`; its containing directory is owner-only. Endpoint values and
raw messages are never logged.

## Layout Policy

V1 supports Kitty's `splits` layout only.

- Detect the originating tab layout through `kitten @ ls`.
- If it is not `splits`, report presentation unavailable and leave the layout
  unchanged.
- `childBias` is the first child-region share: vertical configuration makes the
  first live child a `vsplit` beside the exact orchestrator; horizontal makes it
  an `hsplit`.
- Later children use the opposite split orientation at bias `50`, anchored to a
  successfully presented child still in the exact origin tab. Cleanup-only IDs
  from a provisional launch, recovery, rollback, closure, or moved child cannot
  be anchors. Vertical selection prefers the greatest `lines`, then `columns`,
  then lowest ID; horizontal swaps the two dimensions. This balances subdivision
  within the child region rather than repeatedly dividing the orchestrator.
- If no managed child remains in that tab, placement intentionally falls back to
  the exact orchestrator and first-child orientation/bias. Moved children remain
  exact-ID lifecycle-managed but cannot become anchors.

The focused orchestrator-plus-two-child arrangement is live-validated. Broader
multi-child placement scenarios remain to be exercised before extending that
claim.

## Server Reachability

Read `ctx.serverUrl` at launch time. Probe `/global/health` with a short timeout
before opening a split.

The implemented controller uses a credential-free GET with `credentials:
"omit"` and `redirect: "error"`, rejects URL user information, and independently
races fetch plus response JSON parsing against one two-second `AbortSignal`
deadline. Success requires the installed OpenCode 1.18.4 response shape
`{ healthy: true, version: string }` with a non-empty version. Generic 2xx,
non-JSON, false health, and malformed or empty-version bodies are unavailable.
The same captured URL is passed to the adapter only after a successful probe. No
response body or error object is retained or logged.

If unreachable:

- keep the OpenCode child session untouched;
- do not create a Kitty window;
- record a non-sensitive unavailable reason;
- retry only through bounded reconciliation, not a tight loop.

Controller snapshot and timer mutations share one serialized queue. Snapshot
notifications are revision-coalesced, while periodic maintenance has at most one
queued instance. Unavailable children retry no more than once per configured
reconciliation interval. Existing handles are polled only by periodic
maintenance, so status-event traffic cannot accelerate exact-ID broker queries.

Once `open` has returned a valid presentation handle, `exists(handle) === false`
means **close means close** for that child membership lifetime. The controller
clears the handle, sets phase `unavailable` and reason `window-closed`, and never
tries another open while that tracker child record remains. Manual closure and
an immediately exited attach client intentionally have the same behavior. An
authoritative removal followed by a later re-add creates a fresh record that may
open normally. Failures before a handle exists retain interval-bounded retry;
an `exists()` failure retains the handle and continues periodic probing.
Controller snapshots report `desired: "closed"` for the suppressed record and
`desired: "open"` otherwise. Their deprecated `manualReopenAttempts` field is
retained at runtime with value `0` for source compatibility only.

## Cleanup

Cleanup is idempotent.

- Manual Kitty closure (or immediate attach-client exit) removes only the
  presentation handle and suppresses reopening for that membership lifetime.
- OpenCode session deletion closes the associated Kitty window if it exists.
- Plugin `dispose` stops timers, rejects new work, drains or cancels queued
  operations, and closes all managed Kitty windows with bounded concurrency.
- A missing Kitty window is success during cleanup.
- The plugin never deletes OpenCode sessions as cleanup.

The implemented controller uses serial close concurrency to preserve the
broker's one-request-in-flight contract. One absolute 65-second deadline covers
queue drain, controller-owned close attempts, and final adapter disposal; no
phase resets or extends it. Adapter disposal is invoked even after expiry, but
the controller then returns without awaiting it. The contained adapter/broker
operation continues best effort under its own existing bounds and broker
shutdown owns any remaining managed IDs. Repeated calls share one disposal
promise. Snapshot reconciliation re-checks the disposal boundary after every
awaited close and before subsequent map mutation, so work that outlives the
global deadline cannot repopulate controller state after disposal clears it.

Kitty 0.47.4 reports a missing `ls --match=id:<closed-id>` as a command error;
it does not return an empty JSON list. A managed child can also be moved to a
different tab. Existence checks therefore use a full non-mutating `ls` snapshot
and test whether the managed numeric ID occurs exactly once anywhere in the
minimal parsed tree. All titles, commands, environments, and other raw fields
are discarded immediately and never logged. Origin-layout and launch-placement
checks continue to use the exact origin-tab query.

Before every launch, the broker records the exact origin-tab numeric ID set and
validated window dimensions. It chooses only from the intersection of that tab
and broker-managed positive IDs. If the launch runner rejects or times out, or
stdout does not contain a valid returned ID, the broker queries the same tab
again and closes only one uniquely added ID when
all pre-existing IDs remain and that window carries the broker-generated,
per-launch non-secret Kitty user-variable marker. The marker is broker-owned and
never accepted over IPC; lifecycle targeting still uses only the recovered
numeric ID. Any marker mismatch, removal, multiple addition, missing origin, or
other ambiguity is left untouched. Child and orchestrator launch use this same
recovery primitive.

After a successful child launch, its returned positive ID is immediately added
to broker-managed cleanup state before post-launch validation or focus. The
selected anchor must still occur in the post-launch origin-tab snapshot; if it
does not, the broker exact-ID rollback-closes the new window and returns a
sanitized failure for normal controller retry. The ID remains cleanup-managed
even if rollback fails. Only after validation and focus restoration succeed does
the child become placement-eligible; successful close, absence, and shutdown
remove that eligibility while cleanup tracking remains independent.

When launch stdout is malformed or the runner rejects after creating a uniquely
marked window, the shared recovery path synchronously reports that exact ID to
its owner before attempting idempotent recovery close. The child broker records
it for shutdown cleanup, and broker startup records it as the orchestrator for
its `finally` close. Recovery reporting and close failures never replace the
original launch timeout/failure classification.

Shutdown closes managed windows sequentially under one global deadline. The
deadline does not grow with the number of windows. If it expires during an
active bounded subprocess, no additional close starts; the active promise has a
contained rejection handler and is allowed to finish under its own process
bound. Broker sockets also absorb peer errors and never write raw failures when
a client disconnects during an asynchronous response.

## Timeout Budget

Every Kitty subprocess has a 10-second bound. The longest `open` failure path
uses at most five serialized Kitty subprocesses, including validation, focus,
and exact-ID rollback. The named broker operation budget is therefore five
subprocess bounds plus a five-second scheduling margin. Both IPC peers use the
same 60-second default, adding a further five-second transport margin, so a
valid operation completes or rolls back before either peer expires it.

V1 assumes the serialized controller has at most one broker request in flight.
The server enforces this assumption by rejecting an overlapping connection with
a bounded unavailable result rather than queueing it behind an active `open`.
Client and server constructors retain explicit timeout overrides for focused
tests, but production defaults come from the same constant.

Adapter disposal preserves the same one-in-flight invariant. It atomically
rejects new adapter work, waits for all requests that already started under
their existing bounded transport timeout, then sends exactly one shutdown
request. A successful racing `open` therefore returns and becomes broker-owned
before shutdown runs, so it cannot become a handleless window outside cleanup.
Repeated disposal calls share the same promise and do not send another request.

## Logging

Log structured lifecycle transitions and sanitized failures. Never log:

- complete environment maps;
- `KITTY_LISTEN_ON` values;
- Kitty public keys or passwords;
- OpenCode server passwords;
- authentication headers;
- full command lines containing sensitive values.

## Extension Strategy

Future backends implement `PresentationAdapter` and their own availability
checks. Backend selection belongs in configuration. No backend-specific handle
may leak into the session tracker beyond the opaque presentation handle.
